# План оптимизации ruleix

## Цели

- Снизить задержку `Search`, особенно для `Between`, `CompareBy` и вложенных `All`.
- Уменьшить количество аллокаций на запрос.
- Снизить потребление памяти equality-индексами с большим числом уникальных значений.
- Улучшить масштабирование при одновременных `Search` и `Insert`.
- Гарантировать уникальность модификаторов в результатах поиска.
- Сохранить типобезопасность и порядок первого совпадения результатов.

## Этап 0. Зафиксировать базовые показатели

**Статус: выполнено 16 августа 2026 года.** Сценарии находятся в
`benchmark_test.go`, результаты и параметры запуска — в
`BENCHMARK_BASELINE.md`, профили — в каталоге `profiles`.

Перед изменениями расширить benchmarks и сохранить исходные результаты.

Добавить сценарии:

- `Eq`: попадание, промах, wildcard, низкая и высокая кардинальность.
- `GTE`, `LTE` и `CompareBy`: начало, середина и конец диапазона.
- `Between` с большим числом уникальных границ.
- Плоский и вложенный `All`.
- Параллельный `Search`.
- Смешанная нагрузка `Search`/`Insert`.
- Построение индекса и объём занятой памяти.

Для каждого сценария фиксировать:

- `ns/op`;
- `B/op`;
- `allocs/op`;
- профили CPU и памяти на репрезентативном наборе данных.

Команды проверки:

```sh
go test ./...
go test -race ./...
go test -run '^$' -bench . -benchmem -count 5
```

## Этап 1. Устранить повторные обходы в `All`

**Статус: выполнено 16 августа 2026 года.** Каждый дочерний результат
материализуется один раз, пересечения начинаются с фактически наименьшего
bitmap, а пустой дочерний результат останавливает дальнейшую материализацию.
Медиана контрольного benchmark для вложенного `All` снизилась с 10 592 до
5 395 ns/op, аллокации — с 31 до 16. Прямой `Eq` сохранил прежний
профиль аллокаций. Переиспользуемый буфер ранжирования остаётся частью этапа 2.

### Проблема

`allRule.search` сначала вызывает `cardinality` для каждого дочернего правила, а затем повторно вызывает `search`. Для ordered-правил это два обхода дерева. Вложенный `All` может материализовать один и тот же промежуточный результат несколько раз.

### Доработка

- Ввести внутренний search-context со scratch-памятью.
- Материализовать результат каждого дорогостоящего дочернего правила один раз.
- Сортировать дочерние результаты по фактической cardinality.
- Пересекать уже рассчитанные bitmap, начиная с наименьшего.
- Сохранить ранний выход при пустом результате.
- Для дешёвых правил рассмотреть отдельную оценку cardinality без материализации.

### Критерии готовности

- Ordered-правило не обходит один диапазон дважды в рамках одного `All.search`.
- Результаты и порядок ID совпадают с текущей реализацией.
- Нет регрессии в простых `Eq`-запросах.
- Есть отдельные тесты для вложенных `All` и раннего выхода.

## Этап 2. Изменить API `Search` и убрать служебные аллокации

**Статус: выполнено 16 августа 2026 года.** `Search` принимает обязательный
указатель на буфер назначения, `Visit` поддерживает ранний выход, оба API дедуплицируют
внешние ID с сохранением позиции первого совпадения. Малые `All` используют
inline-буфер ранжирования, большие — переиспользуемый pool. В контрольных
equality benchmarks успешный поиск сократился с 4 до 3 аллокаций (аллокация
результирующего среза устранена), вложенный `All` — с 16 до 15 аллокаций.

### Доработка

- Перенести `rankedChildren` в переиспользуемую scratch-память.
- Для небольших групп использовать inline-буфер или специализированный малый контейнер.
- Проверить escape analysis для callback-функций в ordered-обходах.
- Изменить публичный API так, чтобы `Search` всегда принимал вторым аргументом массив для записи результатов:

```go
func (ix *Index[C, ID]) Search(value C, dst *[]ID)
func (ix *Index[C, ID]) Visit(value C, yield func(ID) bool)
```

- `Search` должен записывать результаты в `(*dst)[:0]`, обновляя переданный срез через указатель и переиспользуя его capacity, когда она достаточна.
- Вариант `Search`, самостоятельно создающий результирующий массив, не оставлять: передача массива вторым аргументом обязательна для каждого вызова.
- Обновить все тесты, benchmarks, README и примеры под новую сигнатуру.

### Уникальность результатов

- `Search` всегда должен возвращать уникальный список модификаторов по внешнему `ID`, даже если одинаковый модификатор был добавлен несколькими подходящими правилами.
- При дубликатах сохранять позицию первого совпадения, то есть порядок должен соответствовать первому добавленному подходящему правилу для каждого `ID`.
- Дедупликация должна применяться и к `Visit`, чтобы разные API поиска имели одинаковую семантику.
- Выбрать реализацию дедупликации по результатам benchmark: локальный `map[ID]struct{}` с переиспользованием либо отдельное отображение внешних ID во внутренние уникальные ID.
- Добавить тесты для повторной вставки одного ID, совпадения одного ID через разные ветви правил и повторного использования непустого `dst`.

### Критерии готовности

- `Search` переиспользует переданный вторым аргументом буфер.
- `Search` никогда не возвращает один внешний ID более одного раза.
- Уникальные результаты сохраняют порядок первого совпадения.
- Для типичного успешного запроса устранена аллокация результирующего среза.
- `Visit` поддерживает досрочное завершение обхода.
- README и все примеры используют обязательный второй аргумент `Search`.

## Этап 3. Ускорить диапазонные запросы

**Статус: выполнено 16 августа 2026 года.** Ordered-индексы используют
инкрементально поддерживаемые агрегаты блоков по 128–256 уникальных значений.
Полные блоки объединяются одной bitmap-операцией, отдельно обходятся только
неполные граничные фрагменты. Differential-тесты сравнивают `Between` и все
пять операторов `CompareBy` со сканирующей реализацией на данных, занимающих
несколько блоков.

На контрольном запуске `GTE/Middle` ускорился с 1 211 406 до 133 312 ns/op,
`GTE/End` — с 1 330 768 до 253 388 ns/op, `Between` — с 2 510 153 до
168 543 ns/op. Узкий `GTE/Start` сохранил прежний уровень (192,9 против
182,8 ns/op baseline), equality-путь не использует дополнительные агрегаты.
Построение ordered-индекса из 10 000 уникальных значений занимает около
11,1 ms и 3,33 MB; benchmark сохранён для дальнейшего контроля компромисса.

### Проблема

`orderedIndex.walk` объединяет bitmap каждого подходящего уникального значения. Стоимость широкого диапазона линейна по числу затронутых узлов.

### Исследуемые варианты

1. Блочные prefix/suffix-агрегаты по 64–256 соседних значений.
2. Агрегированные bitmap в поддеревьях.
3. Заморозка изменяемого дерева в отсортированный массив с prefix/suffix bitmap.

Предпочтительный первый эксперимент — блочные агрегаты: они ограничивают рост памяти и не делают каждую вставку слишком дорогой.

### Критерии выбора

- Измерить компромисс между скоростью поиска, скоростью вставки и памятью.
- Сравнить узкие, средние и широкие диапазоны.
- Не принимать вариант, который ускоряет только synthetic benchmark и ухудшает типичную equality-нагрузку.

### Критерии готовности

- Число `Or` для широкого диапазона существенно меньше числа уникальных порогов.
- Семантика строгих и нестрогих операторов покрыта тестами.
- `Between` и все пять операторов `CompareBy` проходят differential-тесты со сканирующей эталонной реализацией.

## Этап 4. Адаптивное хранение equality-значений

**Статус: выполнено 16 августа 2026 года.** Equality posting list хранит один
внутренний ID inline, до 32 ID — в компактном массиве, затем преобразуется в
Roaring bitmap. Порог выбран сравнительными build-benchmarks: при 32 ID на
значение компактное представление занимает около 475 KB/op и 1 936 allocs/op
против 515 KB/op и 4 430 allocs/op при переходе после 16; порог 64 ухудшает
случай 100 ID на значение (490 против 464 KB/op).

Для 10 000 уникальных значений `BenchmarkBuildIndex` снизился с baseline
2,94 MB/op и 79 860 allocs/op до 1,98 MB/op и 29 864 allocs/op. Изолированный
поиск posting list высокой cardinality отличается от прямого Roaring примерно
на 4% (67 против 64 ns/op). Переходы singleton → array → bitmap покрыты
тестами, добавлен benchmark разных cardinality.

### Проблема

Сейчас каждому уникальному значению соответствует полноценный Roaring bitmap, даже если в нём находится один ID.

### Доработка

Ввести внутренний адаптивный контейнер:

- один `uint32` для единственного ID;
- компактный массив для небольшого числа ID;
- преобразование в Roaring bitmap после измеренного порога.

Порог выбрать по benchmark и memory profile, не фиксировать заранее без измерений.

### Критерии готовности

- Существенно снижена память при десятках тысяч уникальных equality-значений.
- Нет заметной регрессии для значений с высокой cardinality.
- Переход между представлениями покрыт тестами.

## Этап 5. Ограничить удержание памяти в bitmap pool

**Статус: выполнено 16 августа 2026 года.** Временные bitmap размером более
64 KiB не возвращаются в pool; размер проверяется до `Clear`, сохраняющего
ёмкость внутренних массивов Roaring. Малые bitmap по-прежнему переиспользуются.
Добавлены отдельные тесты обеих ветвей и benchmark редкого широкого bitmap
среди 127 узких запросов.

### Доработка

- Измерить ёмкость bitmap после широких запросов.
- Не возвращать в pool экземпляры, превышающие выбранный порог.
- При необходимости разделить pool по классам размеров.
- Добавить стресс-тест: редкий широкий запрос среди большого числа узких запросов.

### Критерии готовности

- После всплеска нагрузки retained memory возвращается к ожидаемому уровню.
- Повторное использование небольших bitmap сохраняется.

## Этап 6. Улучшить конкурентную модель

**Статус: выполнено 16 августа 2026 года.** Индекс разделён на две фазы на
уровне типов. `New` возвращает одноразовый `Builder` без методов поиска;
`Build` принимает `iter.Seq2[C, ID]` и возвращает неизменяемый `Index`, на
котором доступны только `Search` и `Visit`. Методы `Insert*`, `Freeze`, тип
`FrozenIndex` и глобальный `RWMutex` удалены.

Для параллельных срезов добавлен `Zip`, проверяющий совпадение длин до создания
итератора. Ошибка валидации во время `Build` не публикует частично построенный
индекс, а builder нельзя использовать повторно. Неизменяемый индекс безопасно
обслуживает конкурентные поиски без блокировки; семантика и миграция API
задокументированы в README и покрыты тестами, включая race detector.

### Проблема

Глобальный `RWMutex` защищал всё дерево и массив значений. Любой `Insert`
блокировал все поиски, а длительные поиски задерживали вставку.

### Рассмотренные варианты

- Batch-вставка под одной блокировкой.
- Метод `Freeze`, создающий read-only индекс с поиском без блокировки.
- Immutable snapshot с атомарной публикацией для read-heavy нагрузки.
- Более мелкие блокировки только после подтверждения contention profile.

Выбрана более строгая immutable-модель сборки: она устраняет contention и
делает невозможность обновлений явной в публичном API.

### Критерии готовности

- `go test -race ./...` проходит стабильно.
- Параллельный benchmark показывает масштабирование чтения.
- Документирована immutable-семантика построенного индекса.

## Этап 7. Рассмотреть замену `go-rbtree`

**Статус: выполнено 16 августа 2026 года.** После внедрения блочных
агрегатов дерево дублировало уже отсортированную структуру. `go-rbtree`
заменён бинарным поиском сначала по блокам, затем внутри блока; временный
адаптер `orderedItem` больше не хранит comparator, а зависимость удалена.

Контрольный `BenchmarkBuildOrderedIndex` для 10 000 уникальных значений
ускорился с медианы 9,78 до 4,17 ms/op (примерно на 57%), память снизилась
с 3,33 до 2,77 MB/op (на 17%), аллокации — с 81 897 до 71 896 (на 12%).
Диапазонные search benchmarks сохранили прежний уровень. Корректность поиска
проверяется также после неупорядоченных вставок, разбиений блоков и повторной
вставки значения.

Это низкоприоритетный этап после оптимизации алгоритмов.

Оценить generic-структуру или специализированный отсортированный индекс, если профили подтвердят заметную стоимость:

- интерфейсных вызовов;
- type assertions;
- временных `orderedItem` при поиске;
- невозможности эффективно хранить диапазонные агрегаты.

Замена зависимости оправдана только при измеримом выигрыше и приемлемой сложности сопровождения.

## Этап 8. Перенести дедупликацию ID в построение индекса

**Статус: выполнено 16 августа 2026 года.** Каждому уникальному внешнему ID
теперь назначается один внутренний `uint32` при `Build`. Повторные правила с тем
же ID добавляются в posting lists под этим каноническим номером, поэтому
результирующий bitmap уже уникален и сохраняет порядок первого появления.
`Search` и `Visit` больше не арендуют и не очищают `map` на каждый запрос;
исключения `Not` применяются одной bitmap-операцией `AndNot`.

Поскольку канонический ID при повторной вставке может оказаться меньше недавно
добавленных ID, компактный equality-контейнер поддерживает сортировку и
проверяет дубликаты бинарным поиском. Отдельные тесты покрывают разнесённые
повторения ID, совпадения через разные ветви, порядок результата и глобальную
семантику `Not`.

На контрольном запуске медиана точного `Eq/LowCardinality/Hit` снизилась примерно
с 217 до 153 ns/op, память — с 256 до 144 B/op, аллокации — с 4 до 3. Для miss
получено около 85 ns/op, 112 B/op и 1 аллокация против 138 ns/op, 224 B/op и 2
аллокаций. `Between` с большим числом уникальных границ ускорился примерно со
169 до 96 мкс/op за счёт удаления поэлементной работы с map после широкого
поиска.

Компромисс перенесён в одноразовую фазу построения: временные аллокации
`BenchmarkBuildIndex` выросли примерно с 1,98 до 2,85 MB/op, оставаясь ниже
исходных 2,94 MB/op. Таблица канонизации не сохраняется в готовом индексе, а
при наличии повторных внешних ID готовый индекс хранит меньше значений и битов.

## Этап 9. Оставить единый equality-фильтр с wildcard

**Статус: выполнено 16 августа 2026 года.** Публичный `EqValue` удалён, чтобы
не предлагать два почти одинаковых equality-фильтра. Единственный `Eq`
принимает `func(T) *V`: конкретное значение использует адаптивный posting list,
а `nil` хранится в отдельном wildcard bitmap и совпадает с любым конкретным
значением поиска. Эта базовая семантика проверяется отдельным тестом и
wildcard benchmark.

## Этап 10. Встроить wildcard в базовые фильтры

**Статус: выполнено 16 августа 2026 года.** `GTE`, `LTE`, `CompareBy` и `Not`
принимают nullable-геттеры и хранят `nil` в собственном wildcard bitmap.
Обёртки `All`, `Between`, `BetweenConstraint`, `Nested` и `Optional` не получили
дублирующих bitmap: `Between` наследует wildcard независимо для обеих границ от
составляющих его `GTE` и `LTE`.

Для `Not` wildcard означает отсутствие запрещённого значения. Конкретное
совпавшее запрещённое значение по-прежнему исключает канонический внешний ID
целиком и не может быть отменено wildcard-записью того же ID. При поисковом
`nil` конкретные запреты не срабатывают.

Медиана `BenchmarkBetweenManyUniqueBounds` сохранилась на уровне 95,0 мкс/op
до и после изменения; `88 452 B/op` и 29 аллокаций не изменились. Вложенный
`All` сохранил 15 аллокаций. Concrete ordered-запросы не получили новых
query-time аллокаций. Выдача 10 000 wildcard-результатов занимает 58–60 мкс/op,
8 340 B/op и 3 аллокации для `GTE`, `LTE`, `CompareBy` и `Not`, практически
совпадая с `Eq/Wildcard`. После исключения аллокаций тестовых указателей из
измеряемого участка `BenchmarkBuildOrderedIndex` показывает медиану 4,43 ms/op,
3,06 MB/op и 71 927 аллокаций. Относительно результата этапа 7 это около +6%
времени и +10% временной памяти, однако в эту разницу входит таблица
канонизации ID из этапа 8; сам wildcard добавляет лишь постоянное число bitmap
на базовый фильтр, а не аллокации на каждую запись.

## Этап 11. Исследовать адаптивное предвыделение при повторном `Build`

**Статус: запланировано.** Целевой сценарий — периодическая полная пересборка
индекса по одной и той же схеме, когда объём и распределение следующего набора
обычно близки к предыдущему. После первой успешной сборки builder мог бы
сохранить только статистику размещения и использовать её как capacity hints
для следующей сборки, например с запасом 5%.

### Архитектурное ограничение

Текущий `Builder` одноразовый, а реализации `Rule` одновременно описывают схему
и хранят изменяемые данные построенного индекса. Простое разрешение повторного
`Build` добавило бы новые записи в предыдущий индекс. Очищать и повторно
использовать его backing storage также нельзя: ранее возвращённый immutable
`Index` может продолжать обслуживать конкурентные запросы.

До внедрения эвристики необходимо разделить:

- неизменяемое описание схемы;
- независимое mutable-состояние каждой сборки;
- компактную статистику предыдущей успешной сборки.

Каждый вызов `Build` должен создавать новое состояние индекса. Между вызовами
разрешено переиспользовать только числовые подсказки, но не карты, срезы или
bitmap предыдущего `Index`.

### Собираемая статистика

Одной оценки числа входных записей недостаточно: записи могут иметь повторные
внешние ID и совершенно разную cardinality полей. Рассмотреть сохранение:

- общего числа обработанных записей;
- числа уникальных внешних ID для `Index.values` и таблицы канонизации;
- числа уникальных значений отдельно для каждого `Include` и `Exclude`;
- числа значений и блоков каждого ordered-индекса;
- размеров ID-массивов `Between`;
- распределения записей между ветками `CompareBy`;
- при подтверждённой пользе — размеров equality posting lists.

Подсказки обновлять только после полностью успешного `Build`. Ошибка валидации
или досрочно завершившийся входной iterator не должны менять статистику.

### Эвристика и API

Начальный вариант оценки:

```text
hint = previous + max(1, previous / 20)
```

Расчёт должен быть защищён от integer overflow и при необходимости ограничен
верхним пределом. Следует проверить удержание лишней памяти, если следующая
сборка значительно меньше предыдущей.

Сравнить два дополняющих подхода:

1. Автоматические hints из предыдущей успешной сборки для повторяющейся
   нагрузки.
2. Явный `ExpectedEntries` или sized-вариант `Build` для случаев, когда размер
   известен вызывающему коду, но скрыт за `iter.Seq2`.

Явная оценка должна иметь приоритет над исторической. Если повторный `Build`
существенно усложняет семантику обычного builder, рассмотреть отдельный тип
`Rebuilder`, не ослабляя гарантии существующего одноразового API.

### Benchmark-план

Добавить `BenchmarkRepeatedBuild` как минимум для следующих наборов:

- стабильный размер и распределение;
- рост и уменьшение на 5%, 25% и 50%;
- много уникальных ID против большого числа повторов;
- низкая и высокая equality cardinality;
- ordered-индекс с последовательным и случайным порядком значений;
- одновременно живые предыдущий и новый индексы для оценки peak memory.

Измерять `ns/op`, `B/op`, `allocs/op`, peak и retained memory. Отдельно сравнить
глобальную подсказку числа записей со статистикой по узлам схемы.

### Критерии готовности

- Повторный `Build` создаёт независимый immutable `Index` и не изменяет ранее
  возвращённые индексы.
- Для стабильных наборов подтверждено снижение `B/op` и/или `allocs/op` без
  заметной регрессии времени сборки.
- Избыточное резервирование ограничено при резком уменьшении набора.
- Ошибочная сборка не портит hints последующего вызова.
- Семантика конкурентного использования builder/rebuilder явно определена и
  проверена race detector.
- Решение о внедрении принимается по benchmark: простое предвыделение может
  оказаться малозначимым на фоне создания posting lists и построения
  ordered-индексов.

## Порядок выполнения

1. Расширить benchmarks и зафиксировать baseline.
2. Устранить повторные обходы `All`.
3. Перевести `Search` на обязательный результирующий массив, добавить дедупликацию и `Visit`.
4. Провести эксперимент с range-агрегатами.
5. Внедрить адаптивные equality-контейнеры.
6. Ограничить удержание больших bitmap в pool.
7. Разделить построение и неизменяемый поиск на уровне публичных типов.
8. Только после повторного профилирования решать вопрос о замене дерева.
9. Канонизировать внешние ID при построении и убрать query-time дедупликацию.
10. Свести equality API к единственному `Eq` с обязательной поддержкой wildcard.
11. Встроить wildcard bitmap в остальные базовые фильтры без дублирования в обёртках.
12. Исследовать повторный `Build` с независимым состоянием и адаптивными capacity hints.

После каждого этапа запускать тесты, race detector и benchmarks относительно сохранённого baseline. Оптимизацию считать успешной только при подтверждённом выигрыше на репрезентативных данных без регрессии корректности.
