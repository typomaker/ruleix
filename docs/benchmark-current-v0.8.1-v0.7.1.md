# Сравнение `v0.8.2` с `v0.8.1` и `v0.7.1`

Замер выполнен 31 августа 2026 года для релизного кода `v0.8.2` на коммите
`d81c9ca`,
`v0.8.1` (`f941ec3`) и `v0.7.1` (`4755aa0`). Обозначение `0.71` в запросе
интерпретировано как существующий тег `v0.7.1`; тега `0.71` в репозитории нет.
Последующие изменения до тега затрагивали только benchmark, документацию и
lint-оформление и не меняли исполняемое поведение библиотеки.

## Итог

Текущий код заметно быстрее обоих релизов во всех production-shaped search
сценариях. Относительно `v0.8.1` обычный `Index.Search` ускорился на 18,4%, а
warm и parallel `Local` — примерно на 59%. Относительно `v0.7.1` выигрыш
составил 19,7% для `Index.Search` и около 91% для обоих сценариев `Local`.
Обычный поиск также выделяет на 44,3% меньше временной памяти, чем оба релиза.

Время `Build` совпадает с `v0.8.1` и на 1,5% хуже `v0.7.1`, то есть находится
около принятой границы локального шума. Allocation traffic сборки почти не
изменился относительно `v0.8.1`, но остаётся выше `v0.7.1`: +4,9% B/op и
+22,0% allocs/op. Удерживаемая индексом память выросла менее чем на 0,5%.

## Сопоставимость

Production-shaped набор содержит 38 098 constraints и 18 полей. Код данных и
основные циклы `Search`, parallel `Local`, `Build` и retained-memory одинаковы.
После релизов к benchmark-файлу добавились cleanup-вызовы, комментарии и
отдельный adversarial retained-memory сценарий; они не меняют измеренные циклы.
Adversarial-сценарий отсутствует в старых тегах и поэтому не сравнивался.

## Окружение и команды

- Apple M1 Max, macOS 26.6.2 arm64;
- Go 1.26.0;
- версии запускались из отдельных worktree;
- `GOMAXPROCS=1`, без `-race`;
- первый прогревочный запуск `v0.7.1`, пересёкшийся с повторным процессом, был
  отброшен; таблица использует отдельный чистый повторный прогон.

```sh
GOMAXPROCS=1 go test -run '^$' \
  -bench '^BenchmarkProductionShape(Search|Build)$' \
  -benchmem -benchtime=500ms -count=10 .

GOMAXPROCS=1 go test -run '^$' \
  -bench '^BenchmarkProductionShapeParallelLocalBatch100$' \
  -benchmem -benchtime=500ms -count=10 .

GOMAXPROCS=1 go test -run '^$' \
  -bench '^BenchmarkProductionShape(RetainedMemory|LocalRetainedMemory)$' \
  -benchtime=10x -count=8 .
```

## Интерпретация

Крупный search-выигрыш согласуется с ранее принятыми physical-source/candidate
executor и bounded exact-result working set. Нулевые warm-аллокации появились
уже в `v0.8.1`, а текущая версия дополнительно ускоряет exact-cache hit.

Build allocation regression относительно `v0.7.1` не является новым
непрофилированным отклонением: переход к новому search layout и его
`compileAllEqualityClasses` был локализован allocation-профилями в сравнении
`v0.8.1` с pre-release checkpoint. Последующий двухпроходный compiler вернул
основную часть временных аллокаций; текущая разница с `v0.8.1` составляет лишь
0,2% allocations и 0,6% bytes. Рост adaptive Local retained memory связан с
ограниченным четырёхслотовым exact-result working set и остаётся в общем
бюджете 64 KiB; warm retained memory при этом ниже `v0.8.1` на 2,9%.
