# Архитектура индекса Ruleix

Документ описывает текущую реализацию индекса в репозитории. Это не целевой
дизайн и не публичный API-контракт: при изменении реализации документ следует
обновлять вместе с кодом.

## Назначение и модель данных

Ruleix решает обратную задачу поиска: по одному конкретному значению запроса
нужно найти все сохранённые правила, ограничения которых ему соответствуют.
Схема задаётся типизированным деревом `Rule[C]`, построенным из листовых
операторов (`Include`, `Exclude`, ordered-сравнения, `Between`, `CompareBy`) и
конъюнкции `All`.

Основные сущности:

| Сущность | Ответственность |
| --- | --- |
| `Builder[C, ID]` | Хранит декларативную схему и статистические подсказки от последней успешной сборки. |
| `Rule[C]` | Закрытый интерфейс узла: валидация и вставка при сборке, оценка кардинальности и поиск во время запроса. |
| `Index[C, ID]` | Неизменяемое скомпилированное дерево, таблица внешних ID, пул временных bitmap и вынесенные исключения. |
| `Local[C, ID]` | Непотокобезопасный контекст одного потребителя с кэшами результатов и планов между запросами. |
| `Inspector` | Опциональное наблюдение за выбранным представлением и выборочной runtime-телеметрией. |

Внешний `ID` переводится в плотный внутренний `uint32`. Массив
`Index.values` хранит обратное отображение и тем самым задаёт порядок выдачи:
результаты уникальны и возвращаются в порядке первого появления внешнего ID.
Несколько входных записей с одним внешним ID дополняют одно логическое правило.

## Общая схема

```text
Rule-схема + поток (constraint, external ID)
                    |
                    v
          Builder.Build / buildIndex
                    |
        +-----------+------------+
        |                        |
        v                        v
 compiled Rule tree       []external ID
 postings over uint32     dense ID -> ID
        |
        +--> extracted Exclude rules
        +--> immutable/interned bitmaps
        |
        v
 Index.Search / Index.Visit / Local
        |
        v
 candidate planning -> bitmap intersection or ID scan -> exclusions
        |
        v
 external IDs in insertion order
```

## Сборка индекса

`Builder.Build` создаёт новое состояние схемы на каждый вызов. Сборка проходит
следующие стадии:

1. Для каждого узла выделяется стабильный номер, создаются пустые build-time
   структуры и применяются capacity hints от предыдущей успешной сборки.
2. Входной поток читается один раз. Каждая запись валидируется, внешний ID
   дедуплицируется и переводится во внутренний `uint32`, после чего ID
   добавляется во все относящиеся к ограничению postings.
3. `Lossy`-декораторы анализируют собранное состояние и выбирают точное либо
   консервативное приближённое представление в пределах бюджета.
4. Собирается статистика успешной сборки, дерево упрощается: раскрываются
   вложенные `All`, убираются дубликаты и нейтральные узлы.
5. `Inspect` отделяется от обычного hot path. Для выборочно наблюдаемых
   `Local` сохраняется observed-вариант дерева, обычные поиски используют
   вариант без runtime-инструментации.
6. `Exclude` извлекаются из положительного дерева в отдельный список. Это
   позволяет сначала выбрать кандидатов, а затем удалить запрещённые ID, не
   материализуя универсальный положительный posting каждого `Exclude`.
7. Эквивалентные неизменяемые bitmap интернируются. Для `All` компилируются
   физические алиасы и классы повторяющихся equality-результатов, чтобы не
   выполнять одинаковую работу несколько раз.
8. Ordered-структуры и остальные узлы подготавливаются к поиску; Roaring
   bitmap переводятся в copy-on-write режим до публикации индекса.

Новая статистика и snapshots инспекторов публикуются только после полностью
успешной сборки. Ошибка не повреждает ранее построенный индекс и не заменяет
подсказки последней успешной сборки.

## Физические представления

Все postings содержат плотные внутренние ID. Основной формат для средних и
крупных множеств — `roaring.Bitmap`, но equality-индекс экономит память на
малых множествах.

### Equality (`Include`)

Индекс хранит отдельный wildcard posting и отображение конкретного значения в
множество ID. До трёх уникальных значений build-отображение обходится без `map`;
posting одного ID хранится одним `uint32`, небольшие postings — отсортированным
`[]uint32`, а более крупные переводятся в Roaring. Результат запроса — wildcard
плюс posting точного значения. Отсутствующее значение запроса возвращает
только wildcard. После сборки листья с одним, двумя, тремя или четырьмя
конкретными значениями полностью заменяются отдельными immutable unary, binary,
ternary или quaternary структурами. Для четырёх значений ключи восстанавливаются
по ordinal из временной build-map. Готовые структуры удерживают только getter,
wildcard, inline-ключи и postings; build-time `map`, slice и capacity hints в
готовый индекс не входят. При пяти и более значениях сохраняется общее
map-backed представление: строковый miss уже не даёт устойчивого выигрыша от
пяти развёрнутых сравнений и регрессирует на шести.

### Exclusion (`Exclude`)

Хранится equality-индекс запрещённых значений. Отсутствующее сохранённое
значение ничего не запрещает. При запросе posting совпавшего запрета удаляется
из кандидатов либо проверяется напрямую для малого числа ID.

### Ordered-сравнения

`Greater`, `GreaterOrEqual`, `Less` и `LessOrEqual` используют
`orderedIndex`: отсортированные значения сгруппированы в блоки по 64 элемента,
у каждого значения и блока есть posting. Полные блоки объединяются агрегатами,
а граничный блок просматривается по значениям. Для поддерживаемых скалярных
типов и `time.Time` дополнительно строится таблица маршрутизации к логическому
блоку. Prefix sums кардинальностей дают дешёвую оценку диапазона.

### `Between`

Один логический узел содержит два ordered-индекса: нижняя граница проверяет
`stored.from <= query.from`, верхняя — `query.until <= stored.until`. Итогом
является пересечение результатов обеих сторон. Каждая отсутствующая
сохранённая граница является wildcard только для своей стороны.

### `CompareBy`

Узел содержит wildcard posting и до пяти ordered-индексов — по одному для
`EQ`, `LT`, `LTE`, `GT`, `GTE`. Оператор берётся из сохранённого ограничения;
оператор в запросе игнорируется. Подходящие диапазоны выбранных индексов
объединяются с wildcard.

### `All`

`All` не имеет одного фиксированного физического алгоритма. При подготовке
узел описывает возможности детей: дешёвая оценка кардинальности, готовый
posting, фильтрация существующих кандидатов и прямая проверка одного ID.
Исполнитель выбирает стратегию для каждого запроса.

## Выполнение запроса

Обычный листовой запрос получает временный bitmap из `bitmapPool`, заполняет
его через `root.search`, вычитает объединённые исключения и переводит
внутренние ID во внешние через `Index.values`.

Для корневого `All` используется специализированный путь:

1. Дети ранжируются по кэшированной, дешёвой или расчётной оценке
   кардинальности и стоимости выполнения. Нулевой результат завершает поиск.
2. Совпадающие физические equality-результаты дедуплицируются.
3. Узкий начальный набор может проверяться по ID без материализации всех
   дочерних bitmap. Более широкий набор материализуется и пересекается в
   выбранном порядке.
4. На ранних пересечениях возможна остановка по пустому результату или по
   непересекающимся диапазонам bitmap.
5. Исключения применяются напрямую к малому набору кандидатов либо общим
   bitmap после положительной части запроса.
6. Финальные внутренние ID перечисляются по возрастанию, что совпадает с
   порядком первого появления внешних ID.

`Search` добавляет найденные значения в переданный slice. `Visit` выполняет ту
же семантику, но отдаёт значения callback-функции и поддерживает досрочную
остановку.

## Временная память и `Local`

Общий `Index` содержит `sync.Pool` для временных bitmap и буферов ранжирования.
Пулы меняют только scratch-объекты; опубликованные postings неизменяемы.
Слишком большие временные bitmap не возвращаются в пул, чтобы единичный
широкий запрос не поднял постоянный memory floor.

`Index.Local()` добавляет состояние, принадлежащее одному последовательному
потребителю:

- кэши bitmap отдельных фильтров с admission после повторного использования;
- адаптацию небольшого кэша с двух до четырёх записей;
- кэш порядка детей и некоторых готовых результатов `All`;
- общий лимит удерживаемой памяти для child-кэшей, планов и результатов.

`Local.Close` очищает состояние запроса, возвращает внутренний пул индексу и
публикует накопленную выборочную телеметрию. Использование закрытого `Local`
является ошибкой.

## Lossy-представления

`Lossy(rule, MemoryLimit(n))` компилируется во время `Build`. Если точное
представление укладывается в детерминированно учитываемый бюджет, оно
сохраняется. Иначе планировщик выбирает поддерживаемое приближённое
представление. Его контракт:

```text
lossy result ⊇ exact result
```

То есть допустимы ложноположительные результаты, но не ложноотрицательные.
Один `Lossy` вокруг `All` распределяет общий бюджет между поддерживаемыми
листьями. Вложенные `Lossy` образуют дерево жёстких ограничений: сначала
каждое поддерево доводится до собственного локального лимита, затем предок
может выбрать дополнительные дискретные downgrade-шаги в этом поддереве, но
не может вернуть ему память сверх локального cap. Поэтому фактический лимит
поддерева равен минимуму локального ограничения и доступного бюджета предка.
Обычные вложенные `All` разделяют пул ближайшей политики, а граница `Lossy`
сохраняет собственные accounting и `Inspect`. Детали стратегий и формулы memory accounting описаны в
[lossy-index.md](lossy-index.md).

Снапшот политики публикует через `MemoryLimit` фактически доступный лимит после
локального ограничения и ограничений предков. Он и accounted usage принадлежат
одной неизменяемой build-generation; выбранный exact/lossy mode и granularity
публикуются вместе с ними.

Структура `Lossy`-политик валидируется один раз перед чтением записей. Ошибки
некорректной вложенной политики и ошибки планирования используют один
детерминированный schema path (`Lossy/child/All[i]/...`), поэтому диагностика
не зависит от размеров выбранных представлений и не добавляет обход дерева на
каждую входную запись.

## Параллелизм и жизненный цикл

- `Index` неизменяем после `Build`; `Search` и `Visit` можно вызывать
  конкурентно.
- Один `Local` предназначен только для одной goroutine, но разные `Local`
  одного индекса независимы.
- Один `Builder` можно переиспользовать последовательно. Одновременные вызовы
  `Build` требуют внешней синхронизации, поскольку builder обновляет hints.
- Ранее возвращённые индексы не зависят от последующих сборок тем же builder.
- Максимальное число уникальных внешних ID ограничено пространством `uint32`.

## Карта исходного кода

| Файл | Содержимое |
| --- | --- |
| `rule.go` | Закрытый интерфейс правил, общие capabilities и оптимизация дерева. |
| `builder.go` | `Builder`, `Index`, build pipeline, `Search`, `Visit`, `Local`. |
| `eq.go`, `not.go` | Equality и exclusion indexes. |
| `ordered.go`, `ordered_index.go` | Ordered-операторы, блоковый индекс и маршрутизация. |
| `between.go`, `compare_by.go` | Составные ordered-представления. |
| `all.go`, `execution_capabilities.go`, `execution_cost.go` | Планирование и выполнение конъюнкции. |
| `bitmap_pool.go`, `bitmap_intern.go` | Scratch-пулы, Local-кэши, интернирование и equality-классы. |
| `lossy.go`, `canonical_value.go` | Выбор ограниченных по памяти представлений и канонизация значений. |
| `inspect.go` | Build snapshots и выборочная runtime-телеметрия. |

## Инварианты корректности

При изменении архитектуры необходимо сохранять следующие свойства:

- wildcard определяется только `ok == false`; нулевое значение с `ok == true`
  остаётся конкретным;
- внешний ID возвращается не более одного раза и в порядке первого появления;
- точный индекс не добавляет и не теряет совпадения;
- lossy-индекс не теряет ни одного точного совпадения;
- опубликованные postings не изменяются во время поиска;
- ошибка сборки не публикует частично построенный индекс или новый snapshot;
- `Inspect` не меняет результаты и не добавляет инструментирование в обычный
  `Index.Search`/`Index.Visit` hot path.
