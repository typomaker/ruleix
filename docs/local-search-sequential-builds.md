# `Local.Search` после последовательных сборок

## Назначение

`BenchmarkProductionShapeLocalAfterSequentialBuilds` проверяет наблюдение о
том, что production-поиск через `Local` может замедляться с числом
последовательных перестроений индекса. Он использует тот же набор из 38 098
constraints и те же два запроса, что основной production-shaped benchmark.

Benchmark измеряет поколения 1, 2, 4, 8, 16, 32 и 64. Каждый следующий индекс
строится тем же `Builder`, поэтому сохраняются его capacity hints, но сами
индексы независимы. Публикация воспроизводит прикладной lifecycle:

1. `Build` и создание нового `Local` выполняются без write lock;
2. под write lock заменяется только ссылка на текущий `Local`;
3. старый `Local` закрывается после освобождения write lock;
4. новый `Local` прогревается двумя production-запросами;
5. измеряется steady-state поиск этого поколения.

Для каждого поколения выводятся два режима:

- `Direct` измеряет только `Local.Search` и позволяет обнаружить деградацию
  структуры нового индекса или локального кэша;
- `Published` выполняет тот же поиск под uncontended `RWMutex.RLock`, как при
  загрузке опубликованного `Local`, и показывает полную прикладную стоимость
  без конкурирующего `Build`.

Benchmark использует один поисковый worker. В многопоточном приложении каждый
worker по-прежнему должен иметь собственный `Local`: `RWMutex.RLock` вокруг
ссылки не делает один `Local` безопасным для одновременного использования.

Стоимость `Build`, создание `Local`, write lock, закрытие старого `Local` и
warm-up не входят в timed region. Поэтому benchmark диагностирует изменение
steady-state latency между поколениями, но намеренно не измеряет CPU/GC
contention во время параллельно идущей сборки. Если production-деградация не
воспроизводится этим сценарием, следующим отдельным экспериментом должен быть
concurrent build/search soak с временным рядом latency и GC/heap telemetry.

## Воспроизведение

```sh
GOMAXPROCS=1 go test -run '^$' \
  -bench '^BenchmarkProductionShapeLocalAfterSequentialBuilds/' \
  -benchmem -benchtime=500ms -count=5 .
```

Основной сигнал — монотонный либо устойчивый сдвиг `ns/op` поздних поколений
относительно первого. `B/op` или `allocs/op`, появившиеся только у поздних
поколений, считаются отдельной регрессией. Различия до 1–2% нужно считать шумом
и подтверждать более длинным чередующимся прогоном.

## Первый результат

Замер 31 августа 2026 года: Apple M1 Max, macOS 26.6.2 arm64, Go 1.26.0,
`GOMAXPROCS=1`, медианы пяти прогонов по 500 ms.

| Поколение | `Direct`, ns/op | `Published`, ns/op | B/op | allocs/op |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 227,4 | 234,2 | 0 | 0 |
| 2 | 228,5 | 234,2 | 0 | 0 |
| 4 | 228,1 | 235,3 | 0 | 0 |
| 8 | 227,0 | 235,0 | 0 | 0 |
| 16 | 227,0 | 234,8 | 0 | 0 |
| 32 | 227,8 | 234,8 | 0 | 0 |
| 64 | 227,5 | 234,6 | 0 | 0 |

В изолированном steady-state сценарии деградация с поколением не
воспроизвелась. Разброс `Direct` между минимумом и максимумом составил 0,66%,
`Published` — 0,47%; это существенно ниже границы локального шума. Read lock
добавляет около 7 ns/search и также не дорожает с числом публикаций.
