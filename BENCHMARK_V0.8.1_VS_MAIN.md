# Сравнение v0.8.1 и текущей main

Дата замера: 29 августа 2026 года. Последний тег `v0.8.1` (`f941ec3`)
сравнивался с `main` на коммите `02496e5`.

## Итог

На production-shaped наборе текущий `Index.Search` ускорился на 21,9% и
сократил временную память на 44,3%. Число аллокаций не изменилось. Стабильный
warm `Local.Search` замедлился на 3,2%, сохранив нулевые аллокации. Параллельный
Local замедлился на 2,1%, что находится внутри принятой 3%-границы и близко к
шуму этого сценария.

| Сценарий | v0.8.1 | main (`02496e5`) | Изменение |
|---|---:|---:|---:|
| `Index.Search`, время | 42,12 µs | 32,90 µs | **−21,9%** |
| `Index.Search`, память | 73 394 B/op | 40 852 B/op | **−44,3%** |
| `Index.Search`, аллокации | 28 allocs/op | 28 allocs/op | 0% |
| warm `Local.Search`, время, 1 s | 563,9 ns | 586,2 ns | +4,0% |
| warm `Local.Search`, время, 5 s | 566,8 ns | 584,8 ns | **+3,2%** |
| warm `Local.Search`, память | 0 B/op | 0 B/op | 0% |
| warm `Local.Search`, аллокации | 0 allocs/op | 0 allocs/op | 0% |
| Параллельный `Local`, время поиска | 456,5 ns | 466,2 ns | +2,1% |
| Параллельный `Local`, аллокации партии | 1 alloc/op | 1 alloc/op | 0% |

Знак «минус» означает улучшение. Основная таблица использует медианы десяти
прогонов по одной секунде. Так как разница warm `Local.Search` оказалась рядом
с 3%-границей, для него отдельно выполнено по пятнадцать пятисекундных
прогонов; приведённая длинная медиана подтверждает небольшой регресс.

## Сопоставимость

Код `BenchmarkProductionShapeSearch` и
`BenchmarkProductionShapeParallelLocalBatch100` одинаков в сравниваемых
ревизиях. Разница файла бенчмарков между тегом и main состоит из комментариев
и нового adversarial-сценария retained-memory, который в этот замер не входит.

Использован синтетический production-shaped профиль из 38 098 constraints с
18 полями, диапазонами, UUID и категориальными признаками. Последовательный
поиск чередует два заранее созданных запроса. Параллельный сценарий выполняет
партии из 100 поисков пятью воркерами и отдельным `Local` на каждый воркер.

## Окружение и воспроизведение

- Apple M1 Max, macOS 26.6.2 arm64;
- Go 1.26.0;
- версии запускались из отдельных worktree;
- два пятисекундных блока выполнялись в порядке tag → main, затем main → tag;
- замеры выполнялись без `-race`.

Основной прогон, по два блока `-count=5` для каждой версии:

```sh
go test -run '^$' \
  -bench '^BenchmarkProductionShapeSearch/(Index|Local)$' \
  -benchmem -benchtime=1s -count=5 .

go test -run '^$' \
  -bench '^BenchmarkProductionShapeParallelLocalBatch100$' \
  -benchmem -benchtime=1s -count=5 .
```

Длинная проверка warm Local для каждой версии:

```sh
go test -run '^$' \
  -bench '^BenchmarkProductionShapeSearch/Local$' \
  -benchmem -benchtime=5s -count=15 .
```

## Вывод

По обычному `Index.Search` текущая main даёт крупный и устойчивый выигрыш как
по задержке, так и по временной памяти, без изменения числа аллокаций.
Параллельный Local остаётся внутри допустимого порога. Последовательный stable
warm Local находится чуть хуже 3%-границы: регресс невелик в абсолютных числах
(18 ns/op), но подтверждён длинным прогоном и должен учитываться в финальном
решении этапа E.
