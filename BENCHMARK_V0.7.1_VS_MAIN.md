# Сравнение v0.7.1 и текущей main

Дата замера: 24 августа 2026 года. Последний релиз `v0.7.1` сравнивался с
`main` на коммите `6499b0b`.

## Итог

На production-shaped наборе обычный `Index.Search` ускорился на 1,6%, а
долгоживущий `Local.Search` замедлился на 7,5%. Параллельный поиск через
`Local` замедлился на 3,4%. Время сборки и удерживаемая индексом память
практически не изменились, но сборка стала выделять на 2,7% больше памяти и
делать на 21,5% больше аллокаций. Удерживаемая память холодного `Local` выросла
на 69% (на 1 216 байт); для прогретого и адаптивного `Local` рост составил
1,1–1,4%.

1–2% следует считать близкими к шуму локального замера. Результат equality-only
`Index.Search` был шумнее остальных, поэтому его ускорение требует отдельного
подтверждения, если оно важно для решения о выпуске.

## Профиль данных

Использован `production_shape_benchmark_test.go`, одинаковый в обеих версиях:

- 38 098 constraints и `[16]byte` ID;
- 18 полей, включая два временных диапазона, UUID, категориальные признаки,
  версию платформы и AB-тест;
- распределения заполненности повторяют зафиксированный production-профиль;
- поиск чередует заранее созданные запросы, чтобы измерять поиск, а не
  подготовку входных данных;
- параллельный сценарий выполняет партии из 100 поисков пятью воркерами с
  отдельным `Local` на воркер.

Это синтетическое воспроизведение формы и кардинальностей production-данных;
оно не содержит выгрузку пользовательских данных и не моделирует сетевые или
прикладные задержки.

## Окружение и воспроизведение

- Apple M1 Max, macOS arm64;
- Go 1.26.0;
- обе версии запускались из отдельных worktree на одной машине;
- замеры выполнялись последовательно, без `-race`.

```sh
go test -run '^$' \
  -bench '^BenchmarkProductionShape(Search|Build)$' \
  -benchmem -benchtime=500ms -count=10 .

go test -run '^$' \
  -bench '^BenchmarkProductionShape(LocalClose|EqualityOnlySearch)$' \
  -benchmem -benchtime=500ms -count=10 .

go test -run '^$' \
  -bench '^BenchmarkProductionShapeParallelLocalBatch100$' \
  -benchmem -benchtime=500ms -count=10 .

go test -run '^$' \
  -bench '^BenchmarkProductionShape(RetainedMemory|LocalRetainedMemory)$' \
  -benchtime=10x -count=8 .

go test -run '^$' \
  -bench '^BenchmarkProductionShapeShuffledRetainedMemory$' \
  -benchtime=10x -count=8 .
```

## Вывод

Текущий коммит не меняет стоимость обычного `Index.Search` и сборки настолько,
чтобы это было заметно вне локального шума. Для нагрузки на долгоживущий
`Local` есть умеренная регрессия задержки, а для частого создания холодных
`Local` — заметный относительный рост удерживаемой памяти при небольшом
абсолютном увеличении. Перед релизом стоит отдельно оценить, важны ли для
production именно эти два режима; по одному только `Index.Search` блокирующей
регрессии не видно.

## Причина замедления `Local.Search`

Покоммитный прогон локализовал основное ухудшение на `903e729` (`optimize lossy
all search planning`). Этот коммит добавил в `allRule.reuseLocalPlan` вызов
`lookupPlanningBitmap` для каждого дочернего правила сохранённого плана и
поднял `allCandidateScanLimit` с 4 до 8. Production-shaped схема не содержит
lossy-правил, поэтому новые lookup-вызовы всегда дают отрицательный результат,
но выполняются для всех 18 дочерних правил на каждом горячем поиске, прежде чем
код переходит к прежней проверке `cachedBitmapProvider`.

Контрольные замеры на `6499b0b`, по десять прогонов с `-benchtime=500ms`:

| Вариант | Медиана `Local.Search` | Относительно исходного `6499b0b` |
|---|---:|---:|
| Исходный `6499b0b` | 2,642 µs | — |
| Без lossy planning lookup в `reuseLocalPlan` | 2,473 µs | −6,4% |
| Без lookup и с порогом 4 | 2,466 µs | −6,7% |
| `v0.7.1` | 2,457 µs | −7,0% |

Таким образом, почти вся регрессия связана с безрезультатным обходом lossy
planning provider на exact-схеме. Изменение порога даёт лишь малую добавочную
часть в этом профиле. CPU-профиль также относит 7,8% суммарных samples к
`reuseLocalPlan`; строка нового `lookupPlanningBitmap` видна непосредственно в
его горячем цикле. Более поздние inspector-коммиты меняют результат в пределах
шума и не являются первопричиной.
