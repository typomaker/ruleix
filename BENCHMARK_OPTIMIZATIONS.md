# Результаты оптимизации

Сравнение `v0.4.2` и `v0.5.0` на production-shaped наборе из 38 098
constraints с `[16]byte` ID. Для поиска использованы два чередующихся запроса,
подготовленные до запуска таймера. Время — медиана пяти прогонов по 50 итераций
на Apple M1 Max.

| Сценарий | v0.4.2 | v0.5.0 | Изменение |
|---|---:|---:|---:|
| `Index.Search`, время | 115.8 µs | 93.1 µs | −19.6% |
| `Index.Search`, память | 208.2 KB/op | 108.3 KB/op | −48.0% |
| `Index.Search`, аллокации | 74 allocs/op | 33 allocs/op | −55.4% |
| `Local.Search`, время | 36.2 µs | 6.8 µs | −81.2% |
| `Local.Search`, память | 152.4 KB/op | 7.7 KB/op | −95.0% |
| `Local.Search`, аллокации | 50 allocs/op | 7 allocs/op | −86.0% |
| `Build`, время | 44.6 ms | 33.3 ms | −25.4% |
| `Build`, память | 14.83 MB/op | 4.51 MB/op | −69.6% |
| `Build`, аллокации | 311 254 allocs/op | 24 587 allocs/op | −92.1% |

Главный эффект — уменьшение временных bitmap-аллокаций при поиске и устранение
дублирующихся структур в индексе. Наиболее заметный выигрыш даёт прогретый
`Local`, но обычный конкурентно-безопасный `Index.Search` также стал быстрее и
примерно вдвое сократил память на запрос.

## Unary/binary equality specialization

Сравнение общего `eqRule` до оптимизации с build-time специализациями на том
же Apple M1 Max. Набор содержит 38 098 ID; приведена медиана пяти прогонов с
`-benchtime=200ms`. `RootSearch` измеряет только выбор и материализацию posting
list, `IndexSearch` также преобразует все совпавшие внутренние ID в результат.

| Сценарий | Старый `eqRule` | Специализация | Изменение |
|---|---:|---:|---:|
| Unary `RootSearch` | 14.76 ns | 14.00 ns | −5.1% |
| Binary `RootSearch` | 15.28 ns | 14.33 ns | −6.2% |
| Unary `IndexSearch` | 207.0 µs | 208.3 µs | +0.6% |
| Binary `IndexSearch` | 106.3 µs | 104.6 µs | −1.6% |
| Unary retained rule memory | 112 B | 72 B | −35.7% |
| Binary retained rule memory | 152 B | 112 B | −26.3% |

Полный поиск unary практически полностью определяется обходом 38 098
результатов, поэтому разница lookup находится в пределах шума. Специализация
добавляет во время build одну аллокацию (80 B для unary, 112 B для binary), но
после освобождения общей структуры каждый готовый фильтр удерживает на 40 B
меньше.

Воспроизведение:

```sh
go test -run '^$' -bench '^BenchmarkEqualitySpecialization($|Build$|Retained$)' \
  -benchmem -benchtime=200ms -count=5 .
```
